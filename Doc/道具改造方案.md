# 道具改造方案：从随机获取到携带冷却

> 状态：待实施
> 关联文档：`主策划案.md`、`道具系统子策划案.md`、`设计哲学.md`
> 前置阅读：`设计哲学.md` 的「数据只有浮点一种」「三相事件」「判定顺序」

---

## 一、背景

### 1.1 触发问题

PvP 原型联机跑通后实测：**单局约 18 秒**。而当前道具系统需要玩家记住 13 个道具的完整效果与图标映射，且一局最多只会见到 4~5 个道具。

由此产生的具体失效：

| 问题 | 数据依据 |
| --- | --- |
| 一局抽不完一个 7Bag | 对局 18s，7Bag 需要 7 次获取 |
| 5 个槽位永远填不满 | 5 槽 × 5s 获取 CD = 25s > 18s |
| 「槽位已满则暂停获取」永不触发 | 同上 |
| 每个道具一局最多出现 1 次 | 记忆靠重复建立，1 次不足以形成记忆 |

结论：**系统规模面向 2~3 分钟对局，实际对局只有 18 秒。**

### 1.2 决策

**道具不消耗，携带固定数量（3 个），使用后进入冷却。**

这一改动的实质是把认知负荷从「局中」搬到「局前」：

| 时刻 | 时间压力 | 可承受负荷 |
| --- | --- | --- |
| 局前（选择携带） | 无 | 高：可以读描述、比较、试 |
| 局中（按键使用） | 18 秒 | 必须极低：只能识别图标与键位 |

原先 13 个随机道具把 100% 的负荷压在局中。改为固定携带后，13 个道具全部保留，只是从「被迫承受」变成「主动选择」。

### 1.3 次要目标

1. **展示 GAS 架构能混合效果**：3 个道具同时生效时出现同一 Key 的乘区叠加、修饰被门控压制等情况。
2. **UI 改为状态快照驱动**：修复「增量维护影子状态」导致的潜在错位，符合业内做法。

## 二、目标与非目标

### 2.1 目标

- 道具固定携带 3 个，不消耗，使用后进入冷却
- 每个道具独立冷却，冷却推进速率由全局 `Key.PropCDRate` 修饰
- 删除 7Bag 抽取、获取 CD、槽位上限判定
- HUD 改为「状态快照 → 幂等渲染」
- 保留全部 13 个道具定义与三相事件骨架

### 2.2 非目标（本轮明确不做）

| 项 | 原因 |
| --- | --- |
| 携带数 ≠ 3 | 1 无混合空间，2 偏薄，4~5 回到原问题 |
| 单道具冷却独立修饰 | 需要给 `ModifierSet` 加动态 key，侵入性大。本轮只有全局 `PropCDRate` |
| 携带选择 UI 重构 | 复用现有 `LobbyPanel` 的卡组编辑，只改数量 7→3 |
| 人机模式 | 独立议题，见 `Doc/` 中后续文档。但本方案不阻碍它 |
| 地图改动 | 会污染「认知负荷是否下降」的结论，一轮只改一个变量 |
| 数值平衡 | 第一版沿用统一冷却，打完 10 局再调 |
| 道具重命名 | 「道具」称谓不变，不引入「技能」概念 |

## 三、词汇表

统一以下用词，避免改造期间新旧概念混用。

| 词 | 定义 |
| --- | --- |
| **道具** | 玩家可携带、不消耗、有冷却的能力单位 |
| **携带** | 局前从道具池中选择最多 3 个的动作 |

## 四、核心设计决策

实施时若与本节冲突，以本节为准。

### 4.1 冷却状态存在容器，不存在策略体

```csharp
/// 一个已携带的道具。状态归容器，配置归策略体
public class EquippedProp
{
    public BasePropStrategy prop;
    public float cdMax;    // 来自 prop.cooldown，Init 时读一次
    public float cdRatio;  // 1 = 刚用过，0 = 就绪
}
```

理由：`PropFactory.GetProp()` 每次新建实例，把运行状态放进策略体会让「同一策略多实例」时状态分散；容器本来就在 `Update` 里 tick，状态归属一致。

### 4.2 只修饰冷却速率，永不修饰冷却上限

`Key.PropCDRate` 作用于全部 3 个道具。

这是「冷却存比例而非绝对值」原则的直接推论：

> 比例 = 剩余 / 上限。只改**分子推进速度**（速率），上限恒定，比例语义永远自洽，零同步。

`cdMax` 由策略体配置，任何 Effect 都不应修饰它。若将来需要「某道具冷却变长」，应通过降低**该道具的速率**表达，或扩展为动态 key。

### 4.3 冷却上限来自策略体

```csharp
// BasePropStrategy
/// <summary>
/// 道具冷却时长（秒）。比例 = 剩余 / 该值，该值不参与修饰
/// </summary>
public float cooldown = 4f;
```

与 `name` / `path` / `description` 同层级，由各道具构造函数赋值，风格与现有一致。

### 4.4 使用不再清空道具

`UseProp` 的核心变化只有一行：

```csharp
// 改前：消耗
props[propSlotIndex] = null;
context.prop.OnUse();

// 改后：进入冷却
context.prop.OnUse();
equippedProps[propSlotIndex].cdRatio = Ratio.Full;
```

### 4.5 `CanUse()` 语义不变，但不再有「也不消耗」

```csharp
/// <summary>
/// 道具自身的使用条件。不满足则本次使用不发生，也不进入冷却
/// </summary>
public virtual bool CanUse() { return true; }
```

逻辑层仍然静默 `return`，**不发布任何事件**（保持现有约定）。

玩家的负反馈由 UI 层通过「期待窗口」推断，见 §8.3。

### 4.6 UI 是状态的纯函数

HUD **不再维护任何影子状态**，只做 `Render(snapshot)`。

必须遵守的三条：

| 规则 | 含义 |
| --- | --- |
| 幂等 | 同一份快照调 100 次，结果与调 1 次相同 |
| 不记逻辑状态 | 只保留显示缓存（`fillAmount`、`anchoredPosition` 阻尼值） |
| 位置由下标推导 | `pos = index * (size + spacing)`，不存 `reference` |

### 4.7 元数据与状态分两层传输

| 层 | 频率 | 内容 |
| --- | --- | --- |
| 元数据 | 一局数次 | `name` / `description` / `path` 等字符串 |
| 状态 | 每帧 | 只有数值（比例、层数、buffId） |

理由：`description` 是几十字节字符串，每帧 JSON 序列化 3 次是纯浪费。`buffId` 是不变的身份，天然可作 diff 的 key。

### 4.8 保留「道具」称谓

本项目的人文设定中，这些能力单位仍然叫**道具**。不改为「技能」，不引入职业/技能树语义。

### 5.1 常量

```csharp
// PropContainer

```

### 5.2 `ModifierSet.Key` 变更

| Key | 处理 |
| --- | --- |
| `GetPropCD` | **删除**（获取 CD 概念消失） |
| `GetPropCDRate` | **重命名为 `PropCDRate`** |
| `PropSlot` | **删除**（槽位数量固定为常量） |
| 其余 6 个 | 不变 |

### 5.3 `PropContainer` 目标结构

```csharp
public class PropContainer : NetworkBehaviour
{
    public const int EquippedPropCount = 3;

    // UI 注入委托（沿用现有风格，由 PlayerController / ConnectionProxy 注入）
    public Action<EquipPropEvent> onEquipProp;
    public Action<UsePropEvent> onUseProp;

    private List<EquippedProp> equippedProps = new();

    /// <summary>
    /// 开局注入携带道具。仅服务端调用
    /// </summary>
    public void Init(List<string> propIds) { ... }

    void Update() { ... }        // 冷却推进 + 快照推送
    public void UseProp(int i) { ... }
}
```

**`Init` 职责**：

1. 校验 `propIds.Count == EquippedPropCount`，否则抛异常（快速失败）
2. 逐格 `PropFactory.Instance.GetProp(id)`
3. 绑定四个容器（`gameCharacterController` / `buffContainer` / `effectContainer` / `propContainer`）
4. `cdMax = prop.cooldown`，`cdRatio = Ratio.Empty`
5. 逐格 `onEquipProp?.Invoke(new(){ slotIndex = i, meta = prop.GetMetaData() })`

**`Update` 职责**（仅服务端，`IsLogicDisabled` 时 return）：

```csharp
float rate = modifyPipeline.GetModifierSet().Final(ModifierSet.Key.PropCDRate);
for (int i = 0; i < EquippedPropCount; i++)
{
    if (equippedProps[i].cdRatio > Ratio.Empty)
    {
        equippedProps[i].cdRatio = Ratio.Advance(
            equippedProps[i].cdRatio,
            equippedProps[i].cdMax,
            -Time.deltaTime * rate);
    }
}
```

> `rate` 每帧取一次，**不要在循环内调用 `GetModifierSet()`**。每次调用都会 `ClearModify` 并重算全部 Effect。

**`UseProp(int i)` 流程**：

```
守卫：i 越界 / IsLogicDisabled / cdRatio > Empty / !CanUse()
  → 任一不满足直接 return（不发布任何事件）

三相事件：BeforeUsePropEvent → (cancelled? return) → UsePropResultEvent

执行：prop.OnUse()
      cdRatio = Ratio.Full

三相事件：AfterUsePropEvent
UI 回执：onUseProp?.Invoke(new(){ propSlotIndex = i })
```

### 5.4 `BuffContainer` 需要补的两处

| 变更 | 说明 |
| --- | --- |
| `BuffWrapper` 增加 `float durationInit` | 当前只存剩余 `duration`，无法算比例。`AddBuff` / 叠层时同步写入 |
| 新增 `public void CollectStates(List<BuffState> buffer)` | 供快照构建。**过滤 `!iconVisible` 的 buff** |

无限时长 buff（`duration < 0`）的比例约定为 `1f`。

同时删除 `onBuffAdd` / `onBuffRemove` / `onBuffStackChange` 三个委托字段（由快照取代）。

> `BuffContainer` 内部的三相 buff 事件（`BeforeAddBuff` 等）**保留**，它们是逻辑层的 Hook，与 UI 无关。

### 5.5 快照 DTO

```csharp
/// 单个 buff 的状态（无字符串）
public struct BuffState
{
    public int buffId;
    public int stacks;
    public float remainRatio;   // 剩余时长 / 总时长，无限时长用 1
}

/// 每帧推送的完整 HUD 状态
public struct HUDStateEvent
{
    public float jumpCDRatio;      // 0 就绪 / 1 刚用过
    public float propCD0;
    public float propCD1;
    public float propCD2;
    public BuffState[] buffs;      // 建议复用 List/数组，避免每帧分配
}
```

**为什么不用 `float[]` 装 3 个冷却**：Mirror 的 JSON 路径下数组序列化行为需要额外确认；固定 3 个显式字段零风险，且便于 HUD 侧直接索引。

`buffs` 的排序约定：按 buff 加入顺序，HUD 按此顺序排列图标。

### 5.6 快照推送者

新增 `HUDStatePublisher : NetworkBehaviour`，挂在角色 Prefab 上。

职责：`Update()` 中读取 `GameCharacterController.jumpCDRatio`、`PropContainer` 的 3 个 `cdRatio`、`BuffContainer.CollectStates()`，组装一份 `HUDStateEvent`，交给注入的委托。

```csharp
public Action<HUDStateEvent> onHUDState;
```

- 单人 / Host：`PlayerController` 注入为 `EventBus.Publish`
- 多人：`ConnectionProxy.BindGameObject` 注入为 `EventTransmit`

这一改动**替代原来的 6 个注入委托**（跳跃 CD、道具 CD、槽位数、buff 增/删/叠层），净减少 5 条注入语句。

### 8.2 `Render` 与 `SyncBuffList`

```csharp
/// 幂等渲染，由 HUDStateEvent 触发
public void Render(HUDStateEvent state)
{
    jumpCDImage.fillAmount = Damp(jumpCDImage.fillAmount, 1f - state.jumpCDRatio);
    RenderPropSlot(0, state.propCD0);
    RenderPropSlot(1, state.propCD1);
    RenderPropSlot(2, state.propCD2);
    SyncBuffList(state.buffs);
}

/// 按 buffId 做 diff，任何时刻与快照一致
void SyncBuffList(BuffState[] snapshot)
{
    // 1. 遍历快照
    //    a. 字典已有 → 更新 stacks / remainRatio，SetSiblingIndex(i)
    //    b. 字典没有 → 从 metaCache 取元数据，新建 UI，入字典
    // 2. 遍历字典，凡不在快照中的 buffId → Destroy，移出字典
    // 3. 位置：anchoredPosition.x = index * (size + spacing)
}
```

元数据来源：`BuffMetaEvent` 到达时写入 `metaCache[buffId]`。

**收益**：即使中间漏掉任意数量的状态事件，下一帧自动追平。「对不齐」从架构上不可能发生。

### 8.3 按下与拒绝反馈

`CanUse() == false` 与「冷却未好」在逻辑层都是静默 return，UI 无法直接区分。采用**客户端期待窗口**，服务端零改动：

```
按下数字键 i
  → CmdUseProp(i)
  → HUD.NotifyPropPending(i)      // 开 0.15s 期待窗口

0.15s 内收到 onUseProp（回执）
  → 播放「按下」表现（图标下沉 2px + 1 帧白闪），清除 pending

超时未收到
  → 播放「拒绝」表现（左右甩动 0.1s），清除 pending
```

| 情况 | 现象 | 表现 |
| --- | --- | --- |
| 成功 | 收到回执，`cdRatio` 变 1 | 按下 |
| 冷却未好 | 超时，`cdRatio` 已 > 0 | 甩动 |
| `CanUse()` false | 超时，`cdRatio` 仍为 0 | 甩动 |

不用区分具体原因：玩家的感知统一为「这个键现在不能按」，是认知负荷最低的形态。

**已知限制**：网络延迟 > 150ms 时会误判为拒绝。人机模式与局域网不触发。可后续通过服务端回执 RPC 解决。

### 8.4 局内与局外的信息分工

| 场景 | 显示 |
| --- | --- |
| 局中（HUD） | 只有图标与状态。无文字、无 hover 描述 |
| 局前（大厅携带） | 完整描述 + 图标 + 冷却数值。复用现有 `SectionSlot` + 详情栏 |
| 局后（结算） | 可显示各道具使用次数，用于验证「一局每道具约 4 次」 |

`BuffDescription` 组件不删除，从 HUD 移交给大厅使用。

### 8.5 状态反馈清单

| 时机 | 表现 | 优先级 |
| --- | --- | --- |
| **就绪瞬间** | 图标 scale 1 → 1.15 → 1（0.15s，`OutBack`）+ 白色闪 | **最高**，当前完全缺失 |
| 冷却中 | 图标 `color = 0.35 灰` + 扇形遮罩（`Filled / Radial360`，12 点起逆时针） | 高 |
| 按下 | 图标下沉 2px + 1 帧白闪 | 中 |
| 拒绝 | 左右甩动 0.1s + 描边闪红 | 中 |

「就绪瞬间」收益最大：玩家不需要盯冷却条，只在余光里接收一次闪动。

### 8.6 布局原则（本轮只做结构，不做美术）

| 元素 | 做法 |
| --- | --- |
| 跳跃 CD | 底部中央，宽约 360px、高 6px，方向为「满→空」表示冷却中 |
| 道具栏 | 跳跃 CD 上方，3 个 96×96 方块，间距 16px，总宽与跳跃 CD 对齐 |
| 键位 | TMP 文本，右下角，不依赖 `Sprite[]` |
| buff 图标 | 道具栏左上方一行，48×48，间距 8px |

**本轮不使用任何新美术资源**，全部由 Unity 内置 `UISprite` + TMP 实现。美术替换放到信息层级验证通过之后。

## 十、初始数值

| 项 | 值 | 理由 |
| --- | --- | --- |
| 携带数 | 3 | 见 §2.2 |
| 所有道具冷却 | **4 秒** | 20s ÷ 4s = 每道具一局约 4 次 ≥ 形成记忆的门槛 |
| `PropCDRate` 基准 | 1.0 | 与 `JumpingCDRate` 同构 |
| 携带池 | 现有 13 个道具 | 不删内容 |

**冷却不是平衡数值，是学习数值。** 第一版不做任何个体差异，打满 10 局后再调。

### 10.1 需要重新调整的持续时长

原数值来自消耗品时期，取消消耗后覆盖率会大幅上升：

| 道具 | 原持续 | 不消耗后估算 |
| --- | --- | --- |
| 疾行凝胶 | 3s（原 25s 才能再获得，覆盖 12%） | 冷却 4s → 覆盖约 75% |
| 不偏矢 / 锚爪 | 「下一次跳跃」 | 冷却 4s、跳跃 CD 约 5s → 几乎每次跳跃都挂上 |

**建议方向**：持续时长 ≈ 冷却时长，使覆盖率落在 50% 左右，让「什么时候按」重新成为决策。

第一版**不动**这些数值，先观察实际感受，再统一调。

## 十三、设计经验记录

本次改造沉淀出一条可复用的结论，建议同步进 `设计哲学.md`：

### 13.1 UI 是状态的纯函数

> UI 不维护状态，只渲染状态。

反例（改造前）：`PlayerHUD` 用 `propCache` / `propCDCache` / `jumpCDProgressCache` / `buffWrappers[].reference` 维护了 6 份服务端真值的副本，只能靠「事件一个不漏」保持一致。漏一个即永久错位，且无自愈机制。`OnOpen` 里的全量重置补丁，本身就是「增量维护不可靠」的承认。

正例（改造后）：一份快照 + 幂等 `Render` + 按 id diff 的列表同步。任何时刻 UI 与快照一致。

推论：

| 场景 | 做法 |
| --- | --- |
| 列表类 UI（buff / 道具 / 玩家） | 按 id diff，不按数量增减 |
| 位置类 UI | 由下标推导，不存绝对坐标 |
| 进度类 UI | 接收比例，不接收剩余秒数 |
| 面板重开 | 不需要重置缓存，因为不存在缓存 |

### 13.2 元数据与状态分离

字符串元数据「变更时发一次」，数值状态「每帧发」。混在一起会把序列化开销按帧数放大。

### 13.3 只修饰速率，不修饰上限

比例的语义是「剩余 / 上限」。只改分子推进速度，上限恒定，则比例永远自洽、零同步。这是「冷却存比例而非绝对值」原则的直接推论。
